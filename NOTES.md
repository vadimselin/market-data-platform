## Спринт 0.2 — 2026-08-02

**Вопрос:** Почему `grep` в связке через `|` работает быстрее и на файлах любого размера, а pandas на большом CSV падает с нехваткой памяти?
 
**Сделал:**
- Полигон: 5 CSV по 2000 строк (~/projects/bash-lab)
- Просмотр без открытия: `head`, `tail`, `wc -l`
- Конвейеры: `cat | grep | wc -l`, сравнение с `grep -c`
- Колонки через `awk -F',' '{print $2}'`, агрегация `sort | uniq -c`
  — это буквально GROUP BY
- Перенаправление: `>`, `>>`, `2>`, `2>&1`, `/dev/null`
- Коды возврата `$?`, цепочки `&&` и `||`
- Разобрался с алиасами (oh-my-zsh), многострочным вводом

**Застрял на:** `time(...)` без пробела → zsh ругается про glob qualifier.
`time` — отдельное слово, пробел обязателен.

**Ошибся:** думал, `grep -c` считает совпадения. Он считает СТРОКИ,
в которых есть совпадение. `echo "BTC BTC" | grep -c BTC` → 1.
Совпадения считает `grep -o BTC | wc -l` → 2.

**Ответ на вопрос:** pandas загружает файл в RAM целиком, потому что
строит таблицу с произвольным доступом (сортировка, join, обращение
к любой строке). Конвейер работает потоково: труба между процессами —
буфер 64 КБ, в памяти в каждый момент только он. Когда буфер полон,
ядро приостанавливает писателя, пока читатель не разгребёт (backpressure).
`wc` не хранит строки — только счётчик, поэтому размер файла не важен.

Замеры:
  cat *.csv | grep BTCUSD | wc -l   → 0.011s, 144% CPU (3 процесса параллельно)
  grep -c BTCUSD *.csv              → 0.007s,  78% CPU

**Открытые хвосты:**
- `sort` не потоковый — блокирует конвейер, льёт на диск.
  Связать с блокирующими операциями в плане SQL-запроса (Фаза 4)
- скрипт с `set -e` и аргументами — перенос в 0.3
- почему `uv run` работает без активации venv
- чем `uv.lock` отличается от `pyproject.toml` по точности
- перенести NOTES.md внутрь репозитория

## Спринт 0.3 — 2026-08-05

**Вопрос:** можно ли в одном `grep` совместить исключение и поиск?


**Сделал:**
- Тренировка конвейеров на полигоне bash-lab
- `sort -u` вместо `sort | uniq`
- `awk` с условием: `$2=="BTCUSDT" {print $3}` — это WHERE внутри awk
- Агрегация в awk: `{sum+=$3; n++} END {print sum/n}`
- Массивы в awk: `sum[$2]` — GROUP BY в один проход

**Ошибки, на которых учился:**
- `1$` вместо `$1` — доллар идёт ПЕРЕД номером поля
- `END` вне одинарных кавычек → шелл счёл его именем файла.
  Вся программа awk должна быть внутри кавычек целиком
- Опечатка BTCUSB вместо BTCUSD → grep нашёл 0 строк →
  деление на ноль в awk. Синтаксис был верный, данных не было
- `grep` по нескольким файлам добавляет префикс `имя_файла:` к строке —
  это ломает нумерацию колонок в awk. Подавляется флагом `-h`

**Ответ на вопрос:** нет. `-v` инвертирует результат целиком, флаг относится
ко всей команде. Либо два grep через трубу, либо awk — там условия
выражаются логикой: `awk -F',' '$2=="BTCUSDT" {print $3}'` отсекает
и заголовок, и лишние символы за один вызов.

**Понял про инструменты:** grep ищет текст в строке, awk понимает структуру (колонки, типы, условия), для CSV почти всегда уместнее awk.

**Расшифровка флагов:**
  -e = errexit   — выйти при первой команде с ненулевым кодом
  -u = nounset   — ошибка при обращении к необъявленной переменной

  с set -e:    остановился сразу, код 1
  без pipefail: cat нетфайла | wc -l → код 0 (!)
  с pipefail:   тот же конвейер → код 1

**Ответ на вопрос:** Airflow не читает вывод — только код возврата процесса.
Скрипт может напечатать «КАТАСТРОФА» и вернуть 0, таск будет зелёным.
Опаснее всего конвейеры: по умолчанию код берётся от последней команды,
поэтому `curl упал | jq записал пустоту` = успех. Отсюда pipefail.

**Понял про bash:**
- `[` — это команда (синоним test), поэтому пробелы обязательны
- `./script.sh` — точка это путь, не синтаксис. PATH не содержит
  текущую директорию из соображений безопасности
- `source` выполняет в текущем шелле; bash script.sh — в дочернем процессе
- переменная без `export` дочерним процессам не видна (поэтому env её не показывает)
- обратной дороги нет: скрипт не может изменить переменную родителя

## Спринт 0.5 — 2026-08-12

**Вопрос:** куда деваются данные Postgres, когда контейнер удалён?

**Сделал:**
- docker-compose.yml с Postgres 17, проброс порта 5433:5432
- Подключение локальным psql к БД внутри контейнера
- Эксперимент stop vs down — разница на своих данных
- Named volume для данных БД
- healthcheck с pg_isready
- Коды возврата psql, ON_ERROR_STOP

**Ответ на вопрос:** у каждого контейнера свой слой файловой системы поверх
образа. Всё, что пишется во время работы, живёт там и удаляется вместе
с контейнером.
  stop → контейнер существует, процесс не работает → данные целы
  down → контейнер УДАЛЁН вместе со слоем → данные пропали

Решение — volume: хранилище с ОТДЕЛЬНЫМ жизненным циклом, не привязанным
к контейнеру. Два вида:

  named volume — управляется докером, физически лежит ВНУТРИ Linux-VM
    (/var/lib/docker/volumes/...). На маке такого пути нет, в VS Code
    не видно. «Наружу» здесь означает только «вне контейнера»:
    том переживает docker compose down, но наружу в файловую систему
    рабочей машины НЕ вынесен. Смотреть можно лишь через
    docker volume inspect и docker compose exec.
    Быстрый: файловая система нативна для Linux, без прослойки.

  bind mount — подключается конкретная папка с мака (./data:/путь).
    Видна в редакторе, файлы настоящие. Медленнее: каждое обращение
    идёт через прослойку между macOS и VM.

Правило: данные БД — named volume (тысячи мелких файлов, нужна скорость,
не нужна видимость). Код — bind mount (правишь в редакторе, контейнер
подхватывает сразу).
В Фазе 2: dags/ как bind mount, метаданные Airflow как named volume.

**Проверено:**
  без volume: create table → down → up → relation "trades" does not exist
  с volume:   create table → down → up → данные на месте

**Наступил на грабли:** добавил `name: market-data` в YAML → compose
создал НОВЫЙ проект и перестал видеть старые контейнеры. Старый остался
работать и держал порт → "port is already allocated".
Имя проекта — ключ, по которому compose находит свои контейнеры, сети и тома.
Задаётся один раз и не меняется.

**Понял про compose:**
- имя контейнера собирается автоматически: проект(имя директории)-сервис-номер
- своя сеть на проект, сервисы видят друг друга по именам из YAML
- внутри сети общаются по порту 5432, проброс нужен только для доступа с мака
- named volume (docker управляет, быстро) vs bind mount (папка с мака, видно
  в редакторе, медленнее). Правило: данные БД — named, код — bind

**Ловушка psql (аналог set -e в bash):**
  psql -f script.sql               → продолжает после ошибки, вернёт 0
  psql -v ON_ERROR_STOP=1 -f ...   → остановится, вернёт 3
Коды: 1 — ошибка SQL, 2 — нет соединения, 3 — остановка скрипта

**Где что лежит физически:**
- /tmp — на маке, чистится при перезагрузке
- named volume — ВНУТРИ Linux-VM, на маке такого пути нет.
  Смотреть только через docker volume inspect / docker compose exec

## Спринт 1.1 — 2026-08-12

**Вопрос:** почему `python script.py` и `python -m package.script`
дают разный результат при одинаковом коде?

**Сделал:**
- Разобрался с src-layout: почему пакет лежит в src/, а не в корне
- Создал структуру модулей: config/, loaders/, storage/
- Первые модули: settings.py и binance.py с импортом между ними
- Запустил обоими способами

**Понял про структуру:**
- имя пакета через подчёркивания (дефис в Python-идентификаторе запрещён)
- каждый .py файл — модуль, каждая папка с `__init__.py` — пакет.
  Путь через точки = путь по папкам:
  `market_data_platform.config.settings` → src/market_data_platform/config/settings.py
  Аналогия из SQL: пакет — это схема, `schema.table` ↔ `package.module`
- `__init__.py` может быть пустым, это маркер «папка = пакет».
  Без него импорт в современном Python сработает, но папка может
  не попасть в готовый дистрибутив при сборке
- `__pycache__` — кеш байткода, создаётся и обновляется сам, в git не идёт
- деление подпакетов по назначению (config / loaders / storage),
  а не по типу файлов. То же, что слои в dbt: staging → intermediate → marts
- src-layout не даёт импортировать пакет «просто потому что папка рядом» —
  единственный способ импорта — установить пакет. Тестируешь то,
  что уедет в прод

**Ответ на вопрос:** оба сработали, потому что пакет установлен.
Разница не в том, найдутся ли импорты, а в точке отсчёта:
  python file.py       → sys.path[0] = папка файла
  python -m pkg.module → sys.path[0] = текущая директория, поиск по имени пакета
`-m` работает откуда угодно, если пакет установлен. Так запускают код
в контейнерах и в Airflow.

Ловушка проявляется без установки:
  python3 src/.../binance.py  → ModuleNotFoundError

**Что значит «пакет установлен в venv»** (разобрал 2026-08-13):

Главное в одной фразе: Python ищет модули по списку папок — sys.path.
Установить пакет = положить его туда, куда Python смотрит.

  uv run python -c "import sys; [print(p) for p in sys.path]"
  → .../site-packages
  → /Users/vselin/projects/market-data-platform/src   ← вот он

В site-packages моего кода НЕТ. Там только два файла:
  market_data_platform.pth              — одна строка: абсолютный путь к src/
  market_data_platform-0.1.0.dist-info  — метаданные установки

Python при старте читает .pth файлы и добавляет указанные пути в sys.path.
Вместо копирования кода туда положили «записку с адресом».

Отсюда всё:
- работает из любой директории — путь в .pth абсолютный
- правки видны сразу — Python читает мои настоящие файлы, а не копию
  (это и есть editable-режим)
- без установки не работает — нет .pth, нет пути к src/

Обычные библиотеки ставятся иначе — их файлы физически копируются
в site-packages (там настоящая папка с кодом). Логика: чужую библиотеку
не редактируешь, проще скопировать один раз; свой проект правишь постоянно.

Проверено из чужой директории:
  cd /tmp && uv --project ~/projects/market-data-platform run \
    python -m market_data_platform.loaders.binance   → работает

**Мелочь:** `cat file.pth` в zsh печатает `%` в конце — это не часть файла,
так zsh помечает вывод без финального перевода строки.

**Открытые хвосты:**
- (закрыто) sys.path обоими способами запуска — посмотрел
- (закрыто) `__pycache__` в .gitignore — git check-ignore подтвердил:
  правило `__pycache__/` на строке 2. Слеш в КОНЦЕ = «только директория»,
  на любой глубине. Слеш в НАЧАЛЕ (`/build`) — привязка к корню репозитория
- (закрыто) что значит «пакет установлен в venv»


## Спринт 1.2 — 2026-08-16

**Вопрос:** почему настройки нельзя оставить константами в settings.py?

**Сделал:**
- `uv add pydantic-settings` (→ 14 пакетов в uv.lock вместо 2 запрошенных)
- `.env` с кредами (в .gitignore) + `.env.example` шаблон (коммитится)
- Переписал settings.py: класс Settings(BaseSettings) вместо констант
- Починил binance.py под новый способ обращения к настройкам

**Ответ на вопрос:** три причины.
1. Пароль в git — файл коммитится, секрет уезжает в репозиторий навсегда
2. Разные окружения — на маке localhost:5433, в контейнере postgres:5432,
   в AWS другой адрес. Один файл не может быть верным везде
3. Правка требует релиза — поменять адрес БД = поменять код

Решение: код читает настройки, значения приходят снаружи.
Код при этом НЕ МЕНЯЕТСЯ.

**Как работает BaseSettings:**
Читает объявленные поля класса (`Settings.model_fields`), для каждого
ищет источник, приводит к типу, присваивает.

Аннотация `postgres_port: int` — не комментарий. Python её сохраняет
(`__annotations__`), библиотека читает и строит правила валидации.
Описываешь ЧТО хочешь получить, а не КАК разобрать.
Аналогия: `CREATE TABLE (price numeric)` — тип объявляешь, приводит БД.

**Приоритет источников:**
  переменная окружения → .env → значение по умолчанию

Окружение ПЕРЕБИВАЕТ .env — и это правильно: .env есть только на маке,
в контейнере значения приходят через environment: в docker-compose.
Если бы файл побеждал, случайно попавший в образ .env затирал бы
боевую конфигурацию.

Проверено:
  POSTGRES_HOST=from-env uv run python -c "...print(settings.postgres_host)"
  → from-env, а не localhost из .env

**Важно:** .env НЕ активируется и в окружение не попадает.
`env | grep POSTGRES_HOST` → пусто. Это просто текстовый файл,
который читает библиотека своими средствами.

Защита от коллизий имён — префикс:
  SettingsConfigDict(env_prefix="MDP_") → ищет MDP_POSTGRES_HOST
В Airflow так и сделано: AIRFLOW__CORE__EXECUTOR и т.д.

**Fail fast:** мусор в порту → падение при СТАРТЕ с внятным сообщением,
а не через час в момент подключения к базе.

**Значения по умолчанию вычисляются ОДИН РАЗ при импорте:**
  def f(t=time.time())  → все вызовы вернут одно и то же время
  def add(x, bucket=[]) → список общий на все вызовы: [1], [1,2], [1,2,3]

Поэтому нельзя `def f(symbol = settings.default_symbol)` — значение застынет.
Правильно: `def f(symbol: str | None = None)`, а реальное значение читать
в теле: `symbol = symbol or settings.default_symbol`.

Правило: изменяемые объекты и вычисляемые значения не ставят
в значения по умолчанию.

**Диагностика конфига:**
  uv run python -c "
  from market_data_platform.config.settings import settings
  for k, v in settings.model_dump().items(): print(f'{k:20} = {v}')
  "

**Открытые хвосты:**
- проверить валидацию: POSTGRES_PORT=не_число и .env без обязательных полей
